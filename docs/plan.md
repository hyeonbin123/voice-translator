# voice-translator 계획서 (초안, 2026-09-13)

개발 시작 전 계획. 모델 선택은 측정 뒤에 확정하므로, 아래 후보와 수치 목표는 바뀔 수 있음.

## 1. 목표와 범위

영어↔한국어 음성 번역 웹 서비스. 사용자가 말하거나 글자로 입력하면 번역문을 보여 주고 읽어 준다.

**첫 버전에 넣는 것**
- 방향 선택: 한국어→영어, 영어→한국어
- 입력 두 가지: 마이크 녹음(최대 30초), 글자 입력(최대 500자)
- 결과: 인식된 원문, 번역문, 번역문 음성 재생
- 회원가입·로그인(JWT), 내 번역 기록 보기·삭제
- 단계별 걸린 시간 표시 (인식, 번역, 합성)

**넣지 않는 것 (이후 과제)**
- 말하는 동안 바로바로 번역하는 실시간 번역 (첫 버전 뒤 12절의 단계로 진행)
- 영어·한국어 외 언어
- 목소리 복제, 모바일 앱, 클라우드 배포

## 2. 사용 흐름

1. 로그인 (계정이 없으면 가입)
2. 번역 화면에서 방향을 고르고, 녹음 버튼을 누르고 말한 뒤 멈춤 (또는 글자 입력 후 번역)
3. 서버: 음성 인식 → 번역 → 음성 합성
4. 화면: 원문, 번역문, 재생 버튼, 단계별 걸린 시간
5. 기록 화면: 날짜별 목록, 누르면 원문·번역문 다시 보기, 번역 음성 다시 듣기, 삭제

## 3. 구조

```
브라우저 (React + TypeScript)
  └─ 마이크 녹음(MediaRecorder, webm/opus) · 결과 재생
        │ HTTP (JSON, 음성은 multipart 업로드)
FastAPI (비동기)
  ├─ 인증, 번역 기록 API
  ├─ 음성 인식 서비스 ─┐
  ├─ 번역 서비스      ├─ 모델 전용 스레드 풀에서 실행 (이벤트 루프를 막지 않음)
  └─ 음성 합성 서비스 ─┘
        │
PostgreSQL (사용자, 번역 기록)   로컬 볼륨 (번역 음성 파일)
```

- 모델은 API 프로세스 안에서 한 번 불러 두고 계속 씀. 번역 후보 중 로컬 LLM을 고르면 Ollama를 별도 프로세스로 부름
- GPU(RTX 2080 Ti 11GB)를 음성 인식, 번역, 음성 합성, (쓴다면) Ollama가 나눠 씀. 모델마다 VRAM 사용량을 측정 단계에서 함께 기록하고, 동시에 올릴 수 있는 조합인지 확인함

## 4. API (초안)

| 메서드·경로 | 하는 일 |
|---|---|
| `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `GET /auth/me` | 가입·로그인 (rag-doc-qa와 같은 방식, 비밀번호 8자 이상·72바이트 이하) |
| `POST /translate/text` | `{text, source, target}` → 번역문, 번역 음성 주소, 걸린 시간 |
| `POST /translate/speech` | 음성 파일 + 방향 → 인식된 원문, 번역문, 번역 음성 주소, 걸린 시간 |
| `GET /audio/{id}` | 번역 음성(wav) 내려받기. 본인 기록만 |
| `GET /history`, `GET /history/{id}`, `DELETE /history/{id}` | 내 번역 기록 |
| `GET /health` | DB와 모델 상태, 쓰는 모델 이름 |

- 제한: 음성 30초·10MB, 글자 500자. 넘으면 422
- 모든 오류 응답은 화면에서 이유를 보여 줄 수 있게 구분함 (길이 초과, 형식 오류, 모델 준비 안 됨)

## 5. 데이터 (초안)

- `users`: id, email, hashed_password, created_at
- `translations`: id, user_id, mode(text/speech), source_lang, target_lang, source_text, translated_text, stt_model, mt_model, tts_model, 단계별 걸린 시간(ms), created_at
- `audio_files`: id, translation_id, kind(합성 결과), path, duration_ms
- 사용자가 녹음한 원본 음성은 기본으로 저장하지 않음 (개인정보). 저장할지는 결정 사항 (8장)

## 6. 평가 계획

rag-doc-qa처럼 후보와 판단 규칙을 측정 전에 `docs/experiments.md`에 적고, 선택용과 확인용 데이터를 나눈다.

- **데이터**: Google FLEURS (`google/fleurs`, CC-BY-4.0). `ko_kr`, `en_us`의 음성과 전사. 두 언어의 문장이 서로 번역 관계(FLORES 문장)라 번역 참조로도 씀
  - 선택: dev 분할 / 확인: test 분할 (고른 설정만 한 번)
- **음성 인식**: 한국어 CER(글자 오류율), 영어 WER(단어 오류율), 음성 1초당 처리 시간, VRAM
- **번역**: chrF (한국어는 띄어쓰기 영향이 적은 글자 단위 지표가 맞음), 참고용 BLEU, 문장당 지연, VRAM
- **음성 합성**: 합성한 음성을 고른 음성 인식 모델에 다시 넣었을 때의 CER(알아듣기 쉬운 정도), 합성 시간, 사람이 들어 보는 표본 확인
- **전체**: 한국어 음성 → 영어 번역문(또는 반대)을 참조 번역과 비교한 chrF, 단계별 지연 p50/p95
- **속도 목표 (초안)**: 10초 음성의 음성 번역 전체 중앙값 5초 이내 (이 PC 기준)

## 8. 기술 구성

- **백엔드**: Python 3.11, uv, FastAPI, SQLAlchemy 2.0(async) + asyncpg, Alembic, pytest(모델은 가짜로 대체), ruff
- **프론트엔드**: Vite + React + TypeScript, 라우팅(React Router), 서버 상태 관리(TanStack Query), 테스트(Vitest + Testing Library), ESLint
- **실행**: Docker Compose (db, api, frontend). API 컨테이너에서 GPU를 쓰려면 Docker Desktop의 WSL2 GPU 지원을 확인해야 함. 안 되면 API만 호스트에서 실행하는 방법을 README에 둠
- **CI**: GitHub Actions. 백엔드 ruff + pytest(실제 PostgreSQL), 프론트엔드 lint + test + build

| 7. 마무리 | Docker 전체 실행, 새 클론으로 재현, README(측정 결과·설계 판단·한계) | 새 클론에서 README대로 실행됨 |

첫 버전 뒤에 더한 것: 글자 입력의 오타 교정(docs/experiments.md 6절), 실시간 번역(12절).

측정(2~4단계)이 API·화면(5~6단계)에 영향을 주는 이유: 어떤 모델을 쓰느냐에 따라 VRAM 배분, 응답 시간, API 응답 형태가 달라지기 때문. 그래서 측정이 끝나기를 기다리지 않고, 다음 두 가지 약속을 먼저 정해 API·화면을 나란히 만든다 (2026-09-13 수정)
- 모델 인터페이스와 가짜 구현: 실제 모델 없이도 번역 흐름과 API를 만들고 테스트한다
- API 계약(`docs/api.md`): 서버 음성이 없는 경우(음성 합성 실패, 브라우저 음성으로 대체)까지 먼저 정해 두어, 음성 합성 모델 결정이 늦어도 화면을 다시 만들지 않게 한다

모든 API 경로는 `/api` 아래에 둔다 (예: `/api/auth/login`, `/api/translate/speech`). 화면과 API를 같은 주소에서 제공하기 쉽게 하기 위해서다.

## 10. 위험 요소와 대응

- **VRAM 부족**: 음성 인식·번역·합성·Ollama를 동시에 올리지 못할 수 있음 → 측정 때 VRAM을 함께 기록하고, 조합이 안 되면 작은 모델이나 CPU 실행으로 조정
- **MeloTTS 설치 실패**: 오래된 의존성 고정 때문에 다른 패키지와 충돌할 수 있음 → 4단계 초반에 설치부터 확인하고, 안 되면 다른 로컬 TTS나 브라우저 음성으로 전환
- **브라우저 녹음 형식**: 브라우저마다 webm/opus, mp4 등 형식이 다름 → 서버에서 PyAV로 읽을 수 있는지 확인하고, 안 되면 ffmpeg 설치
- **한국어 음성 합성의 숫자·영어 표기**: "3개", "API" 같은 표기를 읽는 방식이 모델마다 다름 → 평가 표본에서 따로 확인
- **라이선스**: NLLB는 비상업 조건. 채택하면 README에 명시
- **GPU를 Docker에서 못 쓰는 경우**: API를 호스트에서 실행하는 방법으로 대체

## 11. 결정이 필요한 것

1. 사용자가 녹음한 원본 음성을 기록에 저장할지 (기본안: 저장하지 않고 인식된 글자만 저장)
2. 음성 합성을 서버에서 할지, 브라우저 내장 음성도 허용할지 (기본안: 서버 TTS를 측정해서 쓰고, 실패하면 브라우저 음성)
3. 번역에 로컬 LLM(Ollama)도 후보로 둘지 (기본안: 둔다. 품질이 좋아도 느리면 규칙에 따라 탈락할 수 있음)
4. 목표 일정 (기본안: 단계당 2~4일, 전체 3~4주)

## 12. 실시간 번역 로드맵 (2026-09-13 추가)

첫 버전은 한 번 녹음하고 번역하는 방식이다. 최종 목표는 실시간 번역이라 세 단계로 넓힌다(사용자 결정). 단계마다 측정 규칙을 먼저 docs/experiments.md에 적고 고른다.

| 단계 | 사용 모습 | 방식 | 완료 기준 |
|---|---|---|---|
| 1. 대화 모드 | 버튼 없이 말하고 멈추면 번역 음성이 나오고, 바로 다음 말을 듣는다 | 브라우저가 말 끝을 판정해 지금의 음성 번역 API로 한 마디씩 보낸다. 판정은 Silero VAD, 1초 조용하면 끝(docs/experiments.md 7절). 번역 음성이 나오는 동안에는 듣지 않는다 | 말을 멈춘 뒤 번역 음성이 나오기까지 중앙값 약 2.5초 이하, 문장이 중간에서 잘리는 비율 5% 이하. 처음 목표는 1.5초였으나 측정에서 두 조건을 함께 만족하는 방법이 없어, 문장을 온전히 번역하는 쪽을 골랐다(사용자 결정) |
| 2. 동시통역 | 말하는 도중에도 원문·번역문 자막이 계속 갱신되고, 번역 음성은 말을 멈춘 뒤 한 번 나온다 | 한 마디의 경계는 대화 모드 그대로 두고, 그 마디의 소리를 웹소켓으로 계속 보내 서버가 그때까지의 소리를 다시 인식·번역해 돌려준다. 두 번 연속 같게 나온 앞부분은 확정해 진하게, 나머지는 흐리게 보인다. 말 끝 뒤 192ms 조용하면 번역·합성을 미리 시작하고 1초 확인 뒤 바로 재생한다(사용자 결정 D10, docs/experiments.md 8절) | 말한 단어가 자막에 나타나기까지 중앙값 1초 이하. 말을 멈춘 뒤 번역 음성까지 중앙값 1.5초 이하를 목표로 실제 서비스에서 잰다 |
| 3. 두 사람 양방향 | 한 화면에서 한국어·영어 화자가 번갈아 말하면 서로의 말로 번역된다 | 대화 모드를 바탕으로 한 마디마다 말한 언어를 자동으로 가려(Whisper, 한국어·영어 둘 중) 상대 언어로 번역한다. 확신이 0.6보다 낮으면 번갈아 말한다고 보고 직전 마디의 반대 언어로 처리한다. 말풍선 목록과 휴대폰용 마주 보기 화면(사용자 결정 D14, docs/experiments.md 10절). 자막이 나오는 동시통역 바탕은 나중 과제 | 확신 기준 이상인 판별의 정확도가 한국어·영어, 1초·2초·전체 모두 99% 이상인 기준 중 가장 작은 것. validation에서 0.6을 골랐고, test에서는 한국어 1초 조각만 98.9%로 조금 못 미쳤다 |
